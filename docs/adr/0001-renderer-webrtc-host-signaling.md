# ADR 0001：WebRTC 在渲染层、信令中继在宿主进程

- 状态：已采纳
- 日期：2026-11-16

## 背景

「聊天通信基于本地 WebRTC」是硬需求。问题在于信令放在哪一层：

- 渲染层是 `dsh-app://app` 的 secure context，Chromium 对 `ws://192.168.x.x` 这类私网明文
  连接按混合内容拦截；`ws://127.0.0.1` 有豁免，但那只覆盖本机。
- DSH 的 webserver 绑 `127.0.0.1`（且 `Config.host` 拒绝通配地址），不可能承载跨机器信令。
- 客户端插件没有 `node:net` / `node:http`，无法自己监听端口。

## 决策

信令由 **host 进程**用 `node:net` 在 `0.0.0.0:<随机端口>` 上跑一个 JSON-lines TCP 中继；
**WebRTC 完全在渲染层**（`RTCPeerConnection` 是 Chromium 原生能力）。
渲染层与「本地宿主」之间用既有 RPC 通道（`tu-bubbles/room/*`）说话。

## 后果

- 渲染层不做任何裸 TCP/WS，绕开混合内容限制；
- 房主需要放行一次 Windows 防火墙提示（首次监听时系统弹出）；
- 聊天内容不经过任何服务器：对端之间的 DataChannel 是 DTLS-SRTP 加密的点对点连接；
- 代价是「进房间」要两跳（渲染层 → 本地宿主 → 对端宿主），但只有信令走这条路，消息不走。

## 被否掉的方案

- 公网信令服务：需求明确「插件自带本地信令」，且引入外部依赖与隐私问题。
- 在 `ctx.webServer` 上挂 upgrade 路由：只能本机访问，跨机器不可用。
- 渲染层直连：被混合内容策略拦死，实测风险高。
