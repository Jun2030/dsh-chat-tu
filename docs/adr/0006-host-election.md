# ADR 0006：房主离开后按成员表自动选举新房主

- 状态：已采纳
- 日期：2026-11-16

## 背景

信令是「房主中转」模型：房主的宿主进程既是信令服务器，也是所有 SDP/ICE 的中转点。
房主一关窗口或退出进程，其他成员之间的信令就断了 —— 虽然已建立的 DataChannel 还能继续收发，
但**新成员进不来、断线的成员连不回、成员表也没人维护**。

产品要求：房主离开后要自动选一个新房主继续，而不是房间直接散掉。

约束：

- 没有中心服务器、没有账号目录服务，成员之间只有一张**通过房主广播的成员表**；
- 成员表里只有 `memberId`、`accountId`、显示名 —— 想「连过去接管」还必须有地址；
- 选举必须在**没有协调者**的情况下得出唯一结论，否则会出现两个房主各开一间房。

## 决策

1. **人人都是候选**：任何 hub 第一次进房间时，就在 `0.0.0.0:0` 开一个常驻 `node:net` 监听
   （standby），把 `地址 = <局域网IP>:<该端口>` 写进自己的成员信息。不在房间里时收到连接一律
   `destroy`，所以它不会在平时被误认为房主。
2. **确定性选举**：继任者 = 成员表里**除旧房主外** `memberId` 字典序最小的成员。
   所有成员看到的是同一份表，因此不需要投票、不需要领导者，结论天然唯一。
3. **沿用房间码与端口**：继任者在自己原来的 `listenPort` 上接管、房间码不变，
   其他人照旧用「地址/房间码」重连；邀请串只需要换个 IP，房间身份不变。
4. **失败兜底**：按候选顺序最多试 3 轮（每轮 1200ms × 轮次退避）；全部失败才报错。
5. **DataChannel 不重建**：已建立的 peer 连接是端到端的，换房主只影响信令，聊天流不断。

## 后果

- 房主退出后约 0.3s 开始换届，正常情况下 1s 内恢复可加入状态；
- 每个成员多占一个监听端口（防火墙要放行；README 已写明）；
- 成员表里多了一个 `address` 字段 —— 它是**可伪造**的，同网段的人可以填别人的地址；
  在当前「局域网内互相信任、无鉴权」的威胁模型下可接受（与 WebRTC 明文 DTLS-SRTP 之外没有额外安全层一致）；
- 如果两人几乎同时进房间、成员表短暂不一致，选举可能选出不同继任者 —— 概率极低，
  缓解手段是「连不上就按候选顺序退避重试」，不会产生两间长期并存的房子。

## 备选

- **固定一台机器当信令服务器**：实现最简单、最稳，但要求「谁先建房谁当主机」的产品语义让位，
  且用户得手动配一台常开的机器；
- **随机/最先加入者继任**：随机不唯一，「最先加入」需要可信的加入顺序（成员表里没有），
  而且新旧成员对顺序的认知可能不同；
- **靠 UDP 广播找新房主**：跨网段不生效（此前已排除广播方案），而且局域网里广播本身也要处理权限。
